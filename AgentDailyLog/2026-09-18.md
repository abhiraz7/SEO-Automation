# AgentLog — 2026-09-18

## Session: VtechSEO Agent plugin built; WordPress connection test — perf, concurrency, and leak investigation

---

### What We Did

**Built the VtechSEO Agent WordPress plugin** (`vtechseo-agent/`), replacing `claude-wp-mcp` as the plugin linked from the app's WordPress connection popup, per yesterday's scoping:
- Trimmed from 11 tool groups / 67 tools down to **4 groups / 23 tools**: `content`, `seo` (Yoast), `media`, `site` (read-only diagnostics + narrowly gated `get_options`/`flush_cache`).
- Dropped entirely: Elementor, Divi, WooCommerce, plugin install/activate, theme switching, user management, site-wide search/replace, and `php_exec` (arbitrary PHP execution) -- none of it exists in this plugin's codebase at all, not just disabled by default.
- Includes the `update_media_alt_by_url` tool scoped in an earlier session (resolves an image's public URL to its WordPress attachment via core's `attachment_url_to_postid()`, for theme-level images like a logo that carry no `wp-image-N` class to read an ID from).
- `get_site_info` now also reports the detected SEO plugin (Yoast vs RankMath vs AIOSEO vs SEOPress) -- directly closes the gap from the 2026-08-09 session where a RankMath site's fix silently wrote to a Yoast meta key nothing read.
- Same token-generation mechanism preserved exactly (`bin2hex(random_bytes(32))` via `add_option()`, which is a no-op on repeat activation) -- confirmed updating the plugin can never regenerate an existing site's token or reset its enabled groups.
- Wrote `vtechseo-agent/README.md` for the *client*, not the dev team -- explains what data leaves their site (one token), how to revoke it instantly, and exactly what each tool group can/can't touch.
- Zipped and wired into `app/routes/wordpress.py`'s download route (`/downloads/vtechseo-agent`, was `/downloads/claude-wp-mcp`); both connection-drawer templates updated to match.

**Caught and fixed a real bug before it shipped**: `app/wordpress.py` was still hardcoded to call the OLD plugin's REST namespace (`/wp-json/cwpm/v1/tool`) even after the new plugin was built registering under `/wp-json/vtseo/v1/tool` -- every existing connection (2 live: `vseo.vtraffic.io`, `examnotespdf.in`) would have silently failed every call. Fixed `_TOOL_PATH` and the `/ping` path; updated stale `cwpm` references in `models.py`'s docstring too.

**Diagnosed three separate problems reported against "Test connection," in order:**
1. **Token allegedly visible in the UI** -- traced every function in the connection-test call path (`test_connection`, `_call_tool`, `resolve_post_id_by_url`, `_resolve_homepage_post_id`); found no code path that interpolates the raw token into any error message, log, or JSON response. Could not confirm this one from static review -- asked the user for the actual Network-tab response body to pin it down rather than guess. **Still open, unresolved.**
2. **"Test connection" stuck for up to 5 minutes**: root-caused to `_resolve_all_pages` running synchronously, inline, before the route ever responded -- for a 138-page project, that's 138 × (0.3s politeness delay + 1-2 real HTTP round-trips) run in the request's own thread. **Fixed**: extracted the resolve loop's site-url dependency off the `WordPressConnection` ORM object (was tightly coupled to the request's own db session), added `_resolve_all_pages_in_background()` opening its own fresh `SessionLocal()`, and switched the test route to `BackgroundTasks.add_task(...)` -- the ping now returns as soon as it resolves, page resolution still happens automatically afterward, just not blocking the response.
3. **What if 4+ people test the same project from different browsers/devices at once**: would have stacked N independent full-project sweeps -- duplicate HTTP request bursts against the client's own site (risking their rate-limiter/WAF) and concurrent SQLite writes to the same `Page` rows (this app's DB tolerates one writer at a time). **Fixed**: added `_active_resolve_sweeps: set[int]`, a process-local in-flight guard keyed by `project_id` -- same shape of fix as the existing `OnPageTask.status == "posted"` guard in `start_site_audit`, born from the same class of real incident (13 billed crawls in 4 seconds from a double-clicked button with no guard).
4. **What if it's stuck for 30 minutes, not 5**: re-examined the pre-fix math against a slow/partially-unresponsive target site rather than the happy path -- `resolve_post_id_by_url` tries multiple post types per page, each capable of eating the full 20s `_TIMEOUT` before falling through, so 30+ minutes was entirely plausible pre-fix. Also found and fixed a *separate*, still-relevant gap: the frontend's `fetch()` call had no timeout of its own, so a genuinely wedged server process or a network stall that never cleanly errors would leave "Testing…" stuck indefinitely with no recovery but a page reload. Added an `AbortController`-based 25s client-side timeout with a clear, specific error message.
