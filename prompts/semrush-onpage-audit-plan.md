# SEMrush-Powered On-Page Audit — Execution Plan

Date: 2026-07-24
Spike discussion that led here: stakeholder wants on-page SEO issues (title,
meta, H1/H2, alt text, canonical, OG/schema, thin content, duplicate title)
sourced from the SEMrush Site Audit API instead of our own crawler-based
rules, since we already pay for SEMrush and the stakeholder doesn't trust
false positives from our own checks. Fixes still get generated by our
existing Gemini pipeline.

## Decisions locked in during the spike

- **`app/audit.py`'s crawler-based on-page rule engine (`run_audit()`) is
  kept in the codebase but stops being called.** Not deleted — it's a
  code-level fallback if SEMrush coverage or cost doesn't work out. No
  user-facing toggle for it; switching back is a code change, not a
  setting.
- **Security checks stay exactly as they are.** `_audit_ssl`,
  `_audit_security_headers`, `_audit_robots_txt` (Task 6.3) already run as
  independent live `httpx` calls, not from crawler or SEMrush data. This
  plan does not touch them.
- **The crawler (`app/crawler.py`) keeps running unchanged** — it still
  does content extraction (feeds Gemini) and WordPress post-ID/type
  resolution. Only the *source of on-page issues* changes.
- **Cost control:** use SEMrush's `snapshot/{id}/issue/{issueId}` endpoint
  (100 units, returns affected-URL lists) rather than `page/{pageId}`
  detail calls (1,000 units/page). "Current value" for each flagged field
  (e.g. the actual title text) comes from our own crawler's already-stored
  `Page` row, not from SEMrush.
- **`Issue` model and the review UI do not change.** Only what populates
  `Issue` rows changes.

Tasks are sized to be pasted one at a time into Claude Code, in order.
Verify each before starting the next.

## Task 1.2 — SEMrush Site Audit client: fetch issues

**Prompt for Claude Code:**
"In `app/semrush_audit.py`, add functions to poll `snapshots` /
`snapshot?snapshot_id=` until a launched crawl finishes, then fetch
`snapshot/{id}/issue/{issueId}` for the issue types we care about (title,
meta description, H1, H2, alt text, canonical, hreflang/OG if present,
duplicate content). Return each issue as `{issue_type_id, affected_urls}`.
Do not call `page/{pageId}` (too expensive — we get current values from our
own crawler's `Page` table instead, in a later task)."

**Files:** `app/semrush_audit.py`

**How you verify:** run against a real domain with known issues (e.g. a
page with no meta description), confirm the returned issue list includes
that URL under the right issue type.

## Task 2.1 — Issue-type mapping table

**Prompt for Claude Code:**
"Add a mapping in `app/semrush_audit.py` (or a new `app/semrush_issue_map.py`
if it gets long) from SEMrush issue-type IDs to our existing `Issue` model's

**Files:** `app/semrush_audit.py` or new `app/semrush_issue_map.py`

**How you verify:** unit-test or REPL-check a handful of real SEMrush
issue-type IDs from Task 1.2's output map to sensible `Issue` rows matching
the schema `run_audit()` already produces.

## Task 3.1 — New job handler: SEMrush on-page audit

**Prompt for Claude Code:**
"Add `app/jobs/handlers/semrush_audit.py`, sibling to the existing

unused but intact."

**Files:** `app/jobs/handlers/semrush_audit.py` (new)

**How you verify:** run the handler manually against a real project, check
the `Issue` table gets populated with rows that look equivalent in shape to
what `run_audit()` used to produce, sourced from SEMrush data.
